# v0.3.3: opt-in full-model PyTorch wrapper and Metal SiLU correction

This release adds the tested resident `VitniModel` wrapper in the experimental
`vitni-torch` 0.1.0a2 package and corrects the tested finite-input Metal
SiLU/SwiGLU overflow, large-divisor and underflow cases. CPU arithmetic,
numerical regime and published CPU anchors are unchanged.

## Explicit opt-in

Install the Python preview from the tagged source (Rust/Cargo required):

```sh
python -m pip install 'vitni-torch[torch] @ git+https://github.com/vitnify/vitni-tensor@v0.3.3'
```

The GitHub release also provides a macOS ARM64 wheel and source archive.
The Python preview is not published to PyPI. Rust users can obtain
`vitni-tensor` 0.3.3 from crates.io; native Metal/Python host sources are in
the tagged repository.

Importing `vitni_torch` does not load a full model, replace normal PyTorch
operations or change global backend/determinism settings. Using it requires an
explicit constructor. The constructor defaults to CPU; the retained Metal
optimizations require explicit selection:

```python
import torch
from vitni_torch import VitniModel

ids = torch.tensor([1, 450, 11781, 338], dtype=torch.int64)
with VitniModel('model.gguf', backend='metal', optimized=True,
               model_id='my-model') as model:
    logits = model(ids)
    receipt = model.generate(ids, n_new=16)
```

The existing SDK's subprocess bridge and default engine selection are
unchanged. The existing Metal receipt CLI still uses its explicit optimized
preset. No automatic model conversion or backend replacement is installed.

## Validated behavior and costs

The resident wrapper calls the actual native engine, retaining weights,
metadata and KV allocations. Each call starts a fresh sequence. Native
Objective-C autorelease scopes release temporary command objects between
requests in a persistent Python process. The CPU owner retains GGUF bytes and
rebuilds borrowed views without file I/O or matrix copies.

The fixed installed research wheel reproduced **24.32 million raw logit
words** exactly across CPU/Metal, including 512-position TinyLlama and
128-position Stories histories and independent pinned CPU captures. Complete
receipts matched CPU, Metal and the frozen standalone controls.

A diagnostic TinyLlama copy with exact finite gate-weight scaling exposed a
silent error: the old optimized backend returned finite logits with
128,000/128,000 words different from CPU. The fixed backend matched all
128,000 and the full CPU receipt. Edge tests checked 49,036 SiLU, 539,396
SwiGLU, 99,446 product-rounding and 28 finite/infinite-division outputs exactly.

All 57 research-wheel tests and 16 Metal regression tests passed on the
physical M3 Max. The final release wheel passed 58 installed-package tests,
including the added import opt-in check. The 11-test TinyLlama CPU contract
also passed locally and runs in Linux/macOS CI. CI's
`VITNI_FULL_MODEL_CPU_ONLY=1` is explicit; it does not count as native GPU
validation. The strict local hardware gate uses `VITNI_REQUIRE_METAL=1`.

Nine rotating-order resident comparisons showed no material regression from
the SiLU correction. Generation medians changed by +0.08% for TinyLlama and
+0.10% for Stories; forward medians were modestly lower. These differences
do not establish a causal speedup. Timings exclude startup/model load; native
timers exclude IPC/file writes/preallocated output, while PyTorch wall time
includes its boundary and allocation costs. The older approximately 2.47x
engine-versus-llama.cpp ratio was not remeasured in this release.

## Limits

The full-model preview is eager, unbatched, inference-only GGUF execution.
Input tokens are CPU int64; returned logits are CPU float32, including when
the native Metal engine computes them. CUDA, gradients, arbitrary/Hugging Face
model conversion, PyTorch MPS allocator/stream integration, full-graph export
and live KV-state migration are outside this API. Context is capped at
`min(model_context,512)`, with explicit Metal type/dimension checks.

This corrects the identified finite-input activation cases. It does not
establish universal IEEE-754 behavior for every engine operation or portable
NaN payloads. This release has not validated the new wrapper or fix on
physical CUDA, larger model families or other Apple GPU generations. The
existing individual PyTorch operators retain their separate numerical-domain
restrictions and compilation/export support.
